# 架构设计

## 1. 架构风格

采用单机微服务模拟架构。每个服务拥有清晰业务边界，实际落地时可以选择：

- 多进程 HTTP 服务。
- 一个 Go Monorepo 内按服务包拆分。
- Docker Compose 编排 MySQL、Redis 和后端服务。

Demo 阶段推荐先使用 Monorepo + 多模块边界，降低启动复杂度；需要演示微服务通信时再拆成多个进程。

## 2. 分层结构

```text
Frontend
  -> API Gateway / BFF
    -> Application Service
      -> Domain Logic
        -> Repository
          -> MySQL / Redis
```

| 层级 | 说明 |
| --- | --- |
| Frontend | 静态页面，负责 UI、表单、状态展示和接口调用 |
| API Gateway / BFF | 鉴权、路由、角色校验、统一错误码、简单聚合 |
| Application Service | 编排跨领域业务流程，例如支付后建单、发货扣库存 |
| Domain Logic | 商品、订单、库存、支付等领域规则 |
| Repository | MySQL 与 Redis 访问封装 |

## 3. 关键依赖

| 组件 | 用途 |
| --- | --- |
| MySQL | 持久化用户、商品、库存、订单、余额、统计数据 |
| Redis | 登录会话、热点商品缓存、幂等键、短期统计缓存 |
| 前端静态服务器 | 承载 HTML、CSS、JavaScript |
| Go HTTP Server | 提供 REST API |

## 4. 数据一致性模型

Demo 单机环境优先使用本地事务保证关键链路一致性。

| 场景 | 一致性策略 |
| --- | --- |
| 下单支付 | MySQL 事务内完成余额扣减、订单创建、库存预扣、成交额更新 |
| 退款 | MySQL 事务内完成订单状态、余额返还、成交额扣减、退款记录 |
| 发货 | MySQL 事务内完成库存扣减和订单状态批量更新 |
| 下架 | 事务内更新商品状态，并基于未完成订单判断是否可转已下架 |

## 5. 状态枚举

### 商品状态

| 编码 | 常量 | 说明 | 买家可见 |
| --- | --- | --- | --- |
| `1` | `ON_SALE` | 在售 | 是 |
| `2` | `PRE_SALE` | 预售中 | 是 |
| `3` | `DELISTING` | 正在下架 | 否 |
| `4` | `OFF_SHELF` | 已下架 | 否 |

### 订单状态

| 编码 | 常量 | 说明 |
| --- | --- | --- |
| `1` | `PLACED_UNSHIPPED` | 已下单未发货 |
| `2` | `SHIPPING` | 配送中 |
| `3` | `RECEIVED` | 已收货 |
| `4` | `REFUNDED` | 已退款 |

## 6. 安全边界

- API 网关统一解析 Token。
- 每个服务仍需校验资源归属，不能只依赖前端传参。
- 买家与卖家资料分表，减少角色混用。
- 余额、成交额、库存等字段只允许后端根据业务动作变更。
